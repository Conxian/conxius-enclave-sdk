# Hardware Signing Provider Matrix (2026)

**Verified:** 2026-10-13
**Scope:** `conxius-enclave-sdk`, `lib-conxian-core`, and their provider adapters  
**Boundary:** Bitcoin-rooted universal-chain signing and authorization. This work introduces no native Conxian token, tokenomics, or Conxian staking incentive; external assets, chains, layers, and independently evidenced staking adapters remain in scope.

This is a support decision, not a product inventory. A platform is supported only when the exact provider path has a hardware-generated non-exportable key, authenticated and fresh evidence, operation/key binding, revocation or TCB-status checks, durable replay protection, negative integration tests on real hardware, and release evidence. API presence, a simulator, a chipset name, or successful compilation is not support evidence.

## Current decision

No hardware provider is production-supported by this repository at this checkpoint. The typed signing boundary fails closed, but the repository does not yet contain a complete provider-issued signer plus verifier path. `UnavailableEnclave` remains the production default.

## Chipset and driver policy

The SDK must not maintain a marketing-derived list of “secure chipsets.” The stable integration boundary is the platform/provider API plus verified evidence:

1. Android discovers StrongBox through the platform API, requests the exact key policy, and verifies the certificate chain, Google root, security level, authorization lists, boot state, patch levels, application identity, challenge, freshness, and revocation status server-side.
2. Apple checks `SecureEnclave.isAvailable`, treats P-256/ML-DSA capabilities independently, and uses an Apple-supported attestation service before any authorization-factor claim. It must not translate a P-256 device signature into a claim that Bitcoin was signed in the Secure Enclave.
3. Linux TPM integrations use the kernel TPM device plus TSS ESAPI/FAPI. The verifier validates EK/AK identity, quote signature, nonce, PCR selection, event-log replay, firmware/TCB policy, and revocation.
4. PKCS#11 integrations pin an approved module digest/path, token serial and manufacturer policy, key attributes, permitted mechanisms, firmware policy, and vendor attestation where available. Labels and version fields are never trust evidence.
5. Confidential-computing integrations verify evidence outside the workload against current provider collateral and a versioned measurement/TCB policy. A TEE measurement does not prove that a particular signing key is non-exportable unless key custody is separately bound.
6. Offline hardware-wallet integrations bind the displayed PSBT, policy, network, inputs/outputs, fee constraints, device/firmware policy, request nonce, and returned public key. QR/USB transport is untrusted.

## Core boundary

`lib-conxian-core` may consume only the SDK's provider-neutral, provider-verified capability and signed response. It must not parse raw vendor evidence, select a driver by chipset name, upgrade inventory metadata into trust, or accept a mock/POC response. The existing `enclave-poc/` is demonstration material and is not production evidence.
