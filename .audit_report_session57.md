### 1.2 Stale Branch Names (CRITICAL)

**Finding**: Every push/PR-triggered workflow (11 of 13) references both `main` AND `master` in its branch filter:

```yaml
on:
  push:
    branches: [ main, master ]
  pull_request:
    branches: [ main, master ]
```

**Affected workflows**: `ci.yml`, `ci-strict.yml`, `codeql.yml`, `coverage.yml`, `hygiene.yml`, `sbom.yml`, `secret-scan.yml`, `security.yml`, `security-strict.yml`, `wasm-runtime.yml`, `wasm-runtime-evidence.yml`

**Reality**: The repository has NO `master` branch. The default branch is `main`, the secondary long-lived branch is `staged`. The `master` reference is dead code — it can never trigger. This means:
- Pushes to `staged` do NOT trigger these workflows. Only `main` pushes do.
- If someone ever created a `master` branch, it would accidentally trigger all workflows, causing confusion.
- This contradicts the documented policy (BRANCH_POLICY.md, GOVERNANCE.md) which references only `main` and `staged`.

**Recommendation**: Replace `[ main, master ]` with `[ main, staged ]` in all 11 workflows. The branch policy calls for CI to run on both `main` and `staged`.

**Exceptions** (workflows that DON'T have this bug):
- `dependency-review.yml` — triggers on `pull_request` types only (no branch filter) — OK
- `release-strict.yml` — triggers on tags only — OK
